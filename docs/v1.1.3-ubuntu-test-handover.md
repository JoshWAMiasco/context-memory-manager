# CMM v1.1.3 — Handover: verify on a real Ubuntu server, fix what breaks

Hand this file to a Claude Code session that has a shell on an **Ubuntu server** (22.04 or 24.04, x64 or arm64) and a
checkout of `context-memory-manager` at the 1.1.3 commit. CMM 1.1.3 was built and tested on macOS only, against the
web server and with a stand-in for LibreOffice. Your job: install it the way a user would, check every 1.1.3 feature
on Linux with real LibreOffice, real `node-pty`, real network clients, and **fix what doesn't work as you go**.

Read this whole file first. The plan with every decision is `docs/v1.1.3-plan-prompt.md`; the guides are
`docs/guides/server-guide.md` and `docs/guides/desktop-guide.md`.

## Ground rules

- **Repo conventions apply** (see `CONTRIBUTING.md`, and "Ground rules" in `docs/v1.1.3-plan-prompt.md`): every route
  through `withApi`, every path through the path jail, file content through the storage pipeline, nothing that
  contacts the internet (`npm run check:offline`), comments and naming like the surrounding code.
- **Fix as you go, with a test.** For each failure: reproduce it, write the smallest test that fails (Vitest in
  `tests/`, or Playwright in `e2e/`), fix it, see the test pass, run `npm run lint && npm run typecheck && npm test`,
  and commit (one fix per commit, message says what was wrong and why). End commit messages with the
  `Co-Authored-By:` line your session is told to use.
- **Branch and push:** work on a branch `v1.1.3-ubuntu-fixes` from the 1.1.3 commit. Do **not** push or open a PR
  unless the maintainer says so; report at the end.
- **Don't widen scope.** Behaviour that works as the plan says but could be nicer goes in the report, not in code.
  Things that are wrong or broken get fixed.
- **Keep the server's data safe.** Use a test storage (e.g. `/srv/cmm-test`) and test accounts. If the server already
  runs CMM for real use, ask before reinstalling over it (`sudo cmm rollback` exists, but ask anyway).
- **Record everything** in the report at the end: what you checked, what passed, what you fixed (commit), what you
  couldn't check and why.

## 0. Prepare

```bash
uname -m; lsb_release -a; node --version   # Node 22 for building; the package brings its own runtime
git log --oneline -1                        # the 1.1.3 commit
git switch -c v1.1.3-ubuntu-fixes
npm ci
npx playwright install --with-deps chromium   # needs internet once; skip on an offline box and say so
```

Install the optional packages the features use, and note their versions:

```bash
sudo apt install -y git acl libreoffice-nogui   # or libreoffice-core + -writer -calc -impress
command -v git setfacl soffice && soffice --version
```

## 1. Automated checks on Linux

```bash
npm run lint && npm run typecheck && npm test
npm run build:web
# Outside the repo, so versioning isn't refused as a nested git repository; with REAL LibreOffice this time:
CMM_E2E_ROOT=/tmp/cmm-e2e npm run test:e2e
```

Expected: everything passes, except the one deliberate expected failure (`encryption-passphrase.web.spec.ts`,
"decrypts the file when the move is confirmed", a known bug from before 1.1.2; leave it). The office test must take
the "converted by LibreOffice" path, not the "needs LibreOffice" path. If `soffice` is installed and the test still
says it isn't, that's a bug in `server/office/libreoffice.ts` detection: fix it.

Then also run `npm run check:offline`. Known noise from before 1.1.3: links in Drizzle's docs, the `package.json`
homepage, and stale `dist/` copies traced into the standalone output (because `server/terminal/index.ts` triggers
whole-project tracing). Anything new from 1.1.3 code is a finding.

## 2. Build the server package and install it like a user

```bash
npx tsx scripts/package-server.ts --arch "$( [ "$(uname -m)" = aarch64 ] && echo arm64 || echo x64 )"
cd dist/cmm-server-1.1.3-linux-*/ && sha256sum -c ../cmm-server-1.1.3-linux-*.tar.gz.sha256 || true
sudo ./install.sh --storage /srv/cmm-test --tls-self-signed --yes
systemctl status cmm --no-pager; journalctl -u cmm -n 50 --no-pager
```

Check: the service starts, migration `0007_user-theme` runs (an existing 1.1.2 database upgrades without errors),
`@xterm/headless` and `@xterm/addon-serialize` are in the package (`ls /opt/cmm/current/app/**/node_modules/@xterm`),
and the setup code is printed. Finish setup in a browser from **another machine on the network**, and create a second
user with the **editor** role for permission checks.

If you can, also put Caddy in front (`deploy/linux/Caddyfile.example`) for the big-download check in 4.

## 3. Feature checks

Use a browser on another machine. For each item, write in the report: ✅, ❌ + fix commit, or ⚠️ couldn't check + why.

### Terminals (turn on in Settings › Security › Terminals)
1. **Screen after reconnect (the 1.1.3 bug fix):** open a terminal, run `claude` (Claude Code) or `htop`, let it draw,
   minimize, wait, reopen; then reload the page; then restart the network on the client for a few seconds. The screen
   must come back whole every time: no stray characters on a blank screen. Also `vim` in the alternate screen.
2. **Path drop:** drag a tree row onto the terminal: its absolute path on the server (`/srv/cmm-test/...`) is typed,
   quoted when it has spaces or quotes, without Enter. Try a name with spaces, `'`, `$`, and a unicode name. Drop a file
   from the client computer: the "no path on the server" message appears. As the **editor** user, terminals are
   unavailable and `POST /api/terminals/<someone else's id>/paths` is refused (403/404).
3. **Docking:** Dock beside the editor, tabs with two terminals, ⌘J/Ctrl+J fold and unfold (and Ctrl+J typed **inside**
   the terminal still reaches the shell), drag the divider to fold, reload keeps it docked, Undock, a narrow window
   floats them. `htop` keeps running and redraws after dock/undock.

### Upload and download (from another machine, then from a "remote" network)
4. **Folder upload:** drop a folder with subfolders, `.DS_Store`, a `.git` folder; and "Upload folder here". Tree
   recreated, junk skipped (count shown). Upload it again: merges, one name-clash question for the whole folder.
5. **Step-up from a remote network:** make the client count as remote (a client outside the LAN, or through Caddy
   with `trustedProxies` and a forwarded public address; see the guide's "Proxies and X-Forwarded-For"). Then: a folder
   upload asks for the password **once**, a single file upload asks every time, and the folder grant doesn't cover
   another folder. Check in the DB that per-file tokens get `used_at` and folder grants expire after 10 minutes.
6. **Selection zip:** select a file and a folder → "Download 2 items as zip" → unzip on the client: right names, right
   content. A multi-GB folder downloads through Caddy without stalling or buffering in memory (watch `ps`/`top`). A zip
   of an encrypted, unlocked folder warns first and contains plaintext; a locked one fails cleanly.
7. **Replace:** in an unversioned folder (old version goes to Trash; "See what changed" compares), in a versioned
   folder (one "Replace … (uploaded)" step; the history opens on it), with an edit made on the server in between
   (refused, nothing overwritten), and a different extension (asks first). Files in an encrypted folder: the replace
   works and the file stays encrypted on disk (`head -c 4 file` shows `CCM1`).

### Viewers
8. **Office:** `.xlsx` (several sheets, dates, a large sheet past the row limit), `.docx` (tables, images, links, one
   with a `javascript:` link: inert), and with real LibreOffice `.pptx`, `.doc`, `.xls`, `.odt`, `.rtf`. First open
   converts (time it), second is instant (cache in `/var/lib/cmm/office-previews`). Two people opening different
   files at once both get their PDFs (conversions are queued). A damaged file says LibreOffice couldn't convert it.
   A file in an encrypted folder is **not** converted (no plaintext PDF in `office-previews`). The service user `cmm`
   must be able to run `soffice` under the systemd hardening in `deploy/linux/cmm.service`: if conversion fails
   only under the service (works as your user), find what the unit blocks (HOME, writable paths, memory) and fix it
   in the unit or in how `server/office/libreoffice.ts` runs it, without loosening the sandbox more than needed.
   Without LibreOffice (`sudo apt remove` it or set `CMM_SOFFICE_PATH=/nonexistent`), the placeholder explains.
9. **Video:** an `.mp4` (H.264) and a `.webm` show a still frame, duration and resolution; nothing plays; a `.mkv`
   or broken file falls back to the plain placeholder.

### Light mode
10. Light, Dark, System from the account menu and Settings › General; System follows the client OS. Sign in from a
    second browser: same theme (it's per user). Reload in Light: no dark flash. The sign-in and lock pages use the last
    theme. Look at every page in Light (explorer, editors, diff, CSV/xlsx, docx, terminal, Backup page, Settings, Trash,
    dialogs) and list anything unreadable; fix clear contrast bugs in `styles/design-tokens.css`. Dark must look
    exactly as before.

## 4. Upgrade and rollback

From a 1.1.2 install (if needed, build the 1.1.2 package from commit `ab4f76d`, the last 1.1.2 commit; there is
no 1.1.2 tag): install 1.1.3 over it, check data,
users, settings and terminals survive, then `sudo cmm rollback` back to 1.1.2 and confirm it still starts with the
1.1.3 database (the new `users.theme` column must not break 1.1.2). If rollback breaks, report it: that's a release
blocker to fix or document.

## 5. Report

End with a short report for the maintainer:

- Environment: Ubuntu version, arch, browser(s), LibreOffice version, Caddy or not.
- A table of the checks above: ✅ / ❌ fixed in `<commit>` / ⚠️ not checked (why).
- The commits on `v1.1.3-ubuntu-fixes`, each with one line on what was wrong.
- Anything that works as designed but should change (not fixed).
- Whether you think 1.1.3 is ready to release on servers.
